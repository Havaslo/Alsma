# VK: предварительная загрузка фотографий контент-плана

Production worker проверяет VK-посты каждые 30 секунд. Фотографии записей
needs_review, approved, scheduled и publish_failed сохраняются через
photos.getWallUploadServer → multipart upload → photos.saveWallPhoto.
Загрузка не вызывает wall.post и не одобряет/планирует публикацию.

AppSetting хранит вложение отдельно для пары сообщество + immutable media
(id/objectId). Ключ версии v1 включает SHA-256 идентификаторов. При смене
изображения или сообщества прежнее вложение не используется. Успешная часть
пакета сохраняется сразу; ошибка не откатывает подготовленные фотографии.
Lease в БД и локальная дедупликация защищают загрузку от гонок. После сбоя
процесса lease освобождается через 10 минут. Ошибки повторяются с паузой.
Вложения/access keys остаются на сервере, административный status endpoint
возвращает только счётчики. Preview не запускает загрузку.

Перед постановкой в расписание все выбранные фото должны быть подготовлены.
При отправке wall.post использует сохранённые вложения и ключ сообщества,
не нуждаясь в пользовательском ключе загрузки. При отсутствии вложения
публикация не должна молча превращаться в текстовую. Результат wall.post
означает принятие VK, а не независимую визуальную проверку вложений; в этой
ветке нет wall.getById, требующего уже истёкшего пользовательского ключа.
Пользовательские фото могут быть удалены/ограничены самим VK или владельцем;
предварительная загрузка не гарантирует бессрочную доступность вложений.

При предпросмотре XLSX с VK-строками открывается модальное окно проверки
доступа. Обновление использует существующий manual server code exchange.
После подтверждения фото начинают готовиться автоматически; сайт можно
закрыть. Создание черновиков разрешено и без токена, постановка в расписание
ждёт подготовки. Новые/заменённые изображения требуют активного доступа.

Проверка без публикации: GET /api/admin/content-factory/plan/photos/status
(только admin site.access/site.manage). Счётчики относятся ко всем активным
VK-планам. Успех загрузки нельзя считать доказательством отображения фото в
посте: визуальный end-to-end тест допустим только в Black Turtle 138003065.
Основное сообщество для технических тестов не использовать.

## Месячный план и пополнение

Автотесты `content-plan-monthly-scenarios.test.ts` переводят часы на 30 дней:
30 разных фото подготавливаются пакетами, посты публикуются в 12:00 Москвы
после отключения доступа к загрузке. Проверены перезапуск в середине месяца,
отсутствие ранней/повторной отправки, новые посты и замена фото после обновления
токена, сохранность прежней очереди, редактирование текста без повторной
загрузки, отмена, удалённое медиа и отзыв wall-права сообщества. Неизвестный
исход отправки требует ручной проверки и не повторяется автоматически.

Создание плана не означает постановку постов в расписание: нужны подготовленные
фото, одобрение и будущая дата/время. Счётчик дополнительно показывает посты,
которые ещё генерируются; их фото пока не входят в число готовых вложений.
Новый/продлённый пользовательский доступ нужен для новых фото; уже
подготовленная очередь не зависит от его срока действия. Это не продлевает
права ключа сообщества и не восстанавливает фотографии, удалённые из VK.

## Рабочая группа: загрузка в альбом (10.11.2026)

Для основной группы выбран отдельный альбом, ID хранится в AppSetting
`vk.photo.album.<groupId>`. Загружаем через photos.getUploadServer,
multipart file1 и photos.save с group_id/album_id. До сохранения вложения
проверяем, что VK вернул owner_id именно сообщества. Данные этой стратегии
хранятся в отдельном пространстве ключей `album.<albumId>.`, поэтому старые
вложения из пользовательских альбомов не могут попасть в новую очередь.

Управление доступно только через административные маршруты:
GET /api/admin/content-factory/plan/photos/albums (чтение),
POST /api/admin/content-factory/plan/photos/album с {"create":true}
(выбрать существующий служебный альбом или создать его один раз).
GET /api/admin/content-factory/plan/posts/:postId/verify читает фактические
вложения уже опубликованного VK-поста. Произвольную группу эти маршруты
не принимают: используется настроенный VK_GROUP_ID.

Важно: фотографии в альбоме сообщества видны после подготовки, до времени
поста. Расписание управляет публикацией записи на стене. Это особенность
выбранного механизма предварительной загрузки, не приватное хранилище.

10.11.2026 выполнен согласованный живой тест через обычную очередь основной
группы: https://vk.com/wall-177090031_13530 . Повторное чтение вернуло ровно
две фотографии с owner_id=-177090031. Статус опубликованного поста сохранён;
удаление теста на стене пользователь выполняет самостоятельно. Ошибки 405
двух других загрузок исчезли после автоматического повтора; итог 4/4 готово.

Диагностика подготовки теперь сохраняет безопасные код/этап/время ошибки и
показывает причину отдельно для каждого изображения. Токены, access_key и
подписанные URL в статус не возвращаются; успешный повтор убирает прежнюю
ошибку. Изменение владельца в ответе VK само по себе не является универсальным
признаком невалидного фото, но для основной очереди выбраны строго собственные
фотографии сообщества, чтобы не зависеть от доступа ключа группы к личным фото.
