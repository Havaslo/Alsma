# Серверное подключение фотографий VK

Подключение использует Authorization Code Flow: браузер получает одноразовый
`code`, а backend обменивает его на пользовательский ключ и сразу проверяет
`photos.getWallUploadServer` для рабочего сообщества. Ключ никогда не копируется
из адресной строки браузера на сервер. `wall.post` и сообщения бота продолжают
использовать существующий ключ сообщества. Запрашивается только `photos`, без
`wall`: ошибка `15/1134` для пользовательского приложения не должна решаться
переводом публикации записи на этот пользовательский ключ.

## Настройка после синхронизации GitHub

1. Нужен принадлежащий владельцу проект приложения VK с разрешённым серверным
   OAuth и доступом к VK API `photos`. Поддержку этого сценария нужно проверить
   в кабинете конкретного приложения. Один лишь ID VK ID приложения для входа
   не доказывает наличие доступа к фотографиям. Если VK не разрешает этому
   приложению серверную выдачу ключа с `photos`, потребуется согласовать доступ
   с VK или использовать другое принадлежащее владельцу подходящее приложение.
   Код не обходит ограничения VK и не использует чужие client_id/client_secret.
2. В защищённых переменных backend Amazi задать:
   - `VK_PHOTO_OAUTH_APP_ID` — ID приложения;
   - `VK_PHOTO_OAUTH_APP_SECRET` — его секрет;
   - `VK_PHOTO_OAUTH_REDIRECT_URI` — точный HTTPS callback, зарегистрированный
     в настройках этого приложения;
   - `VK_PHOTO_TOKEN_ENCRYPTION_KEY` — 32 случайных байта в Base64.
     Сгенерировать локально: `openssl rand -base64 32`. Не добавлять в GitHub.
3. Для текущего production backend callback:
   `https://8dd6f7cf-ea71-419d-a99c-5f6416bace1f--b80b0d0e.projects.amazi.pro/api/vk-photo-connection/callback`.
   Если адрес backend поменялся, использовать его новый адрес. Адрес
   `https://alsma.ru/api/...` сейчас не проксирует backend и не подходит.
   `VK_GROUP_ID` и ключ сообщества должны оставаться настроенными.
4. Пересобрать/развернуть оба приложения из синхронизированной ветки.
5. В рабочей админке открыть «Фабрика контента» → «Контент-план» →
   «Подключить фотографии VK» и авторизоваться аккаунтом с правами в сообществе.
   Код возвращается на backend. Копировать секреты из браузера больше не нужно.
6. Проверить, что карточка фото подтверждает подключение, а `/api/vk/readiness`
   настоящего backend возвращает `publishingCanAttachPhotos:true`.
   Это ещё не проверка видимости фото: в рамках разрешённой тестовой публикации
   отправить один пост, открыть его в VK и проверить фотографию.

Для подключения из preview зарегистрировать callback соответствующей среды.
Разрешённые CORS origins должны содержать точный origin страницы фабрики.
Поскольку база общая, production и preview, которые должны читать одно
подключение для одного `VK_GROUP_ID`, обязаны иметь один и тот же ключ шифрования.
Иначе подключение останется нечитаемым в другой среде. Не меняйте ключ шифрования
уже подключённой группы без последующего переподключения.

## Хранение и срок действия

Подключение сохраняется в существующей таблице `app_settings` под ключом
`vk.photo.connection.<groupId>` с AES-256-GCM и используется отправителем
динамически, без перезапуска после подключения. Миграция БД не нужна.
OAuth state хранится там же в хешированном виде, действует 10 минут и атомарно
удаляется перед обменом кода, включая отказ или отмену. Callback URL не пишется
в автоматический HTTP-журнал. Ответы API и ошибки не возвращают ключи.

Истёкший сохранённый ключ блокируется; отправитель не возвращается молча к
старому ключу из окружения. `VK_PHOTO_UPLOAD_ACCESS_TOKEN` поддерживается как
прежний способ конфигурации, только если сохранённого подключения ещё нет.
Сам перенос браузерного ключа в эту переменную IP-привязку не исправляет.

Срок действия берётся из ответа VK `expires_in` и отображается в админке.
Код не обещает бессрочный доступ и не выдумывает refresh endpoint.
6 ноября 2026 пользователь проверил `photos,offline` для приложения 54873380:
VK вернул `invalid_request / invalid scope`. Кнопка проверки убрана из интерфейса.
Рабочий доступ `photos` выдан на сутки; длительная автономная работа не решена.
Если VK выдаёт ограниченный срок, владельцу
потребуется переподключение. Для полностью автономного долгосрочного сценария
необходимо отдельно получить поддерживаемый VK долгоживущий доступ/механизм
обновления для конкретного приложения.

Если даже после серверного обмена VK возвращает `IP_MISMATCH`, нужно проверить
стабильность и совпадение исходящего IP обмена и последующих запросов на Amazi.
Размещение в одном процессе не гарантирует одинаковый внешний IP платформы.
Пока реальная проверка не пройдена, подключение не сохраняется как рабочее.

## Тестовая группа

Тестовый интерфейс Black Turtle использует то же серверное подключение,
а публикацию записи выполняет `VK_BLACK_TURTLE_TEST_TOKEN` только для группы 138003065. Пользовательскому аккаунту нужны права в обеих группах. Это отдельная
явно подтверждаемая отправка; она не меняет очередь и статусы рабочего поста.
При подключённом серверном сервисе старый endpoint приёма браузерного токена
возвращает `USE_SERVER_PHOTO_CONNECTION`.

Официальный пример серверного Code Flow:
https://github.com/VKCOM/vk-php-sdk#41-authorization-code-flow
Типы ключей фото-методов:
https://github.com/VKCOM/vk-api-schema/blob/master/photos/methods.json

## Запасная проверка без собственного callback

Если VK отклоняет зарегистрированный redirect_uri, карточка подключения содержит
раздел «VK сообщает об ошибке redirect_uri?». Он запускает отдельный Code Flow
со стандартным адресом `https://oauth.vk.com/blank.html`. Это проверяемая
альтернатива, а не гарантия поддержки конкретным мини-приложением.

Администратор открывает созданную ссылку, подтверждает доступ и возвращает полный
адрес страницы VK в защищённое поле админки в течение 10 минут. Принимается только
одноразовый code, а не access_token. Backend обменивает код, проверяет фото-метод
и сохраняет зашифрованный токен. Это однократное подключение: новые изображения
затем загружает сервер. Фактический срок доступа определяется ответом VK.

Состояние привязано к администратору, origin и группе; чужая сессия, повторное
использование, сторонний URL и попытка передать браузерный токен отклоняются.
Реальный успех выдачи кода, срок доступа и сквозная загрузка фото должны быть
проверены отдельно. Тесты с подменённым API не подтверждают разрешения VK.


## Аудит и реальная проверка 6 ноября 2026

Рабочие API-запросы переведены на `https://api.vk.ru/method`. Загрузка выполняется
пользовательским ключом, `wall.post` — ключом сообщества. Сообщения сообщества
для этого пути не требуются. В тестах загрузчик периодически отвечал HTTP 200
с пустым `photo`: это локальная ошибка `PHOTO_UPLOAD_EMPTY`, а не код VK 122.
До вызова `wall.post` разрешено не более трёх попыток с новым адресом загрузки.
Сам `wall.post` автоматически не повторяется.

В процессе аудита выявлены две ошибки проверки результата:

- `wall.getById` нельзя читать ключом сообщества; используется пользовательский ключ.
- VK может скопировать фото в сообщество и изменить owner/id. При несовпадении ID
  проверяются SHA256 изображений из сохранённого фото и вложения записи.
  Загрузка для проверки ограничена HTTPS CDN VK, 10 MiB и 15 секундами,
  перенаправления запрещены. Несовпадение или недоступность проверки означает
  неопределённый результат; автоматическая повторная публикация запрещена.

`/vk-factory-test` доступен также на production, требует администратора с
`site.access` и `site.manage`, использует отдельный ключ и фиксированную группу
138003065. `/vk-photo-diagnostics` остаётся только для подготовки изображения.
`GET /vk-factory-test/posts/:postId` читает безопасные метаданные уже созданной
записи этой группы без повторной отправки. Статусы черновиков рабочего плана
тестовая отправка не меняет.

В production 6 ноября в 22:34 обновлён код; итоговый тест создал
https://vk.ru/wall-138003065_16. Backend подтвердил изображение после публикации;
независимое чтение вернуло фото `-138003065_457239022` с 11 размерами.
Запись 15 также содержит фото, но первоначальная проверка ошибочно выполнялась
ключом сообщества. Проверка расписания в основной группе 177090031 в этот тест
не входит; её настройки не изменялись.

Доступ к фото истекает **7 ноября 2026 в 20:40 по Екатеринбургу**.
Успешный сквозной тест не снимает это ограничение: бессрочная автономная работа
не подтверждена, неподдерживаемый scope `offline` не используется.
