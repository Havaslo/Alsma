# AI content factory: generation behavior

## Scope and access

The feature serves the administrator content-factory page at `/admin/content-factory`. Its existing authorization requires `site.access`, `site.manage`, or `*`. Calls run through the backend and the connected Amazi AI Gateway; provider credentials never reach the browser. Generated items are drafts. Approval records a human's permission to publish but does not call a social-platform publishing API or send content to a channel.

## XLSX content plan and review gate

- `POST /api/admin/content-factory/plan/preview` accepts a raw XLSX file and its file name, parses it server-side with SheetJS, and returns a validated preview. It stores nothing and makes no AI call. The route accepts up to 10 MiB; a file may contain at most 50 non-empty publication rows. The parser scans for the template's header row so the title and instruction rows above it are allowed.
- Required columns: `Дата публикации`, `Тип публикации`, `Площадка`, `Формат`, `Тема / заголовок`. Optional columns: `Для кого пост`, `Что рассказать (условия, ключевые факты)`, `Призыв к действию / ссылка`, `Стиль и ограничения`, `Промт для изображения`, and `Исходное изображение (файл или рекомендация)`. A time column is optional; missing times default to 12:00. Rows are one post per channel. Supported labels map to `vk`, `telegram`, `max`, `instagram`, `zen`, or `blog`; unsupported channels fail preview with a row-specific error.
- The explicit `POST /api/admin/content-factory/plan/generate` action creates a `ContentPlanImport` and one `ContentPlanPost` per validated row, with status `queued`. The browser doesn't send the XLSX to AI. Text generation uses one `gpt-4.1-mini` Chat Completions request per post, including the row's confirmed facts/conditions, post type, topic, audience, CTA, style limits, image prompt and source-image recommendation, plus the channel writing profile. At most two per-post requests run concurrently; results and errors are persisted independently.
- The queue uses database status compare-and-set (`queued` → `generating`) so dev and production workers sharing the project database cannot both claim the same row. `GET /plan/posts` resumes queued work and requeues `generating` rows that have been stale for five minutes. A successful post enters `needs_review`; failures enter `generation_failed` and can be retried individually.
- `PATCH /plan/posts/:postId` permits changes only for `needs_review` or `approved` posts. Any edit resets approval and requires a new review. `POST /plan/posts/:postId/approve` atomically transitions only `needs_review` to `approved`, recording `approvedById` and `approvedAt`; generation errors and already approved rows cannot be approved again. Manual additions from the content editor also enter `needs_review`.
- Imported image prompts and source-photo recommendations are retained for the review card but do not generate an image. Reviewers can edit title, text, date and time before approval. Social publishing and image creation are not performed by this import workflow.
- Cancellation is a soft status change (`cancelled`) so the content and source row remain available in history. Updating an approved post clears its approval metadata. Calendar records are shared between authorized administrators.

## Models and image context

- Text: `gpt-4.1-mini` via Chat Completions, with the generation task, selected channel IDs, selected reference image bytes as an `image_url` data URI, and the channel-specific copy/image/gallery profiles. `POST /generate/task` stores a text-generation job and returns its ID immediately; `GET /generate/task/:jobId` is scoped to the creating administrator and returns `pending`, `processing`, `completed`, or `failed`. The AI request runs outside the browser request, and its three editable draft variants are persisted until the interface polls the result. Stale processing jobs are marked failed after five minutes.
- The creation form includes `Блог сайта` as a destination. Its adaptation is written as a full article rather than a short social caption; selecting it carries the channel through draft editing, saving, image preparation, and content-plan creation. If the model omits the blog adaptation, the service falls back to the article-style Zen adaptation, then to the main text, instead of rejecting the entire response. Blog delivery is the internal site-content publisher described below, not an external social API.
- Text refinement: authenticated `POST /api/admin/content-factory/generate/refine` accepts the current text, original task, selected channels, free-form user instruction or one of four editing actions, source-photo metadata, and a size-limited base64 JPEG. It uses the same text model and channel profiles, returns a replacement main text and per-channel adaptations, and does not publish. Whole-post actions update the main text and selected-channel adaptations. The channel-adaptation panel sends just one channel and exposes direct AI actions to regenerate or shorten its text, plus a rewrite dialog for a free-form instruction. The frontend updates and saves only that channel's adaptation; if draft persistence fails, the edited content remains in the workspace for a manual save.
- Image: `gpt-image-2` uses Gateway `/v1/images/edits` and `/v1/images/generations` at `medium` quality. Each requested variant begins as one square master generated from the post text, optional image prompt, and source-photo references. The square is reused unchanged for 1:1 profiles; portrait 4:5 profiles are created by extending that square with a transparent canvas and an alpha mask, then the untouched square center is restored so the model cannot replace its text or core scene. Wide 16:9 profiles are a single landscape edit based on the same square master, because the wider composition needs rebuilding; the prompt asks the model to retain the same scene and exact headline. Thus the images for one variant stay visually related across channels rather than being generated as unrelated scenes. The editor selects one photo at a time from source materials; the API accepts up to four references for future multi-reference workflows. Repeated runs append results rather than replacing existing channel galleries. Every final image receives the contrast-matched ALSMA logo after aspect fitting, is stored as PNG in project object storage, and is registered in `content_factory_media`. AI-guided outpainting can still vary at the extension seam; it does not guarantee pixel-perfect preservation outside the restored square.
- Image generation is asynchronous: `POST /generate/image` stores a server-side job and returns its ID immediately; `GET /generate/image/:jobId` returns `pending`, `processing`, `completed`, or `failed`. The job stores reference-photo object IDs and generation metadata in PostgreSQL. Temporary source images are deleted after completion or failure. Status reads are scoped to the administrator who created the job. A stale processing job is marked failed after five minutes, allowing the interface to show a retry message rather than wait forever.
- Image-generation reference images are prepared as JPEG in the browser and their combined Base64 representation is limited before JSON transport. The server validates the Base64 payload and actual JPEG signatures before storing inputs or starting a provider request. Other reference-image actions keep their existing limits.
- The explicit extra image prompt can request changes to the scene, including adding people or props. Without an explicit request, the model preserves the recognizable source setting; it must not present unconfirmed prices, offers, amenities, or services as factual.
- The text refinement photo is also signature-validated as JPEG after strict Base64 validation. The frontend limits the prepared JPEG to 7 MiB so its JSON/Base64 representation fits the existing 12 MiB JSON request limit.
- Image-generation jobs persist `image_count` with a backward-compatible default of 1, plus `mode` and a JSON array of reference-photo descriptors; older single-reference job fields remain supported. The editor polls the server-side job until it succeeds or fails, then appends the result to each selected channel's image gallery on the selected variant and saves that updated draft. Channels with the same output dimensions (currently Telegram/MAX square and VK/Instagram portrait) reuse the same crop. If saving the draft fails, generated images remain in the media library and the UI asks the administrator to save the draft manually. Generated results can be added from the media library to source materials for another editing iteration.

## Channel profile behavior

`content-factory-guidelines.ts` is the shared backend source of truth returned by `GET /api/content-factory/guidelines` and interpolated into both generation prompts.

| Channel    | Copy style                                                      | Test image ratio and output  | Gallery behavior noted to the model                                                                                                                    |
| ---------- | --------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| VK         | Clear lead, short paragraphs, checked facts, one natural CTA    | 4:5; 1080×1350; JPEG/PNG     | Multiple post attachments exist; do not promise a universal swipe carousel                                                                             |
| Telegram   | Compact, conversational, readable line breaks                   | 1:1; 1200×1200; JPEG/PNG     | Bot API `sendMediaGroup` albums require 2–10 items                                                                                                     |
| MAX        | Short standalone message, direct and factual                    | 1:1; 1200×1200; JPG/JPEG/PNG | Up to 12 media attachments per message per MAX docs; call it a group of attachments, not an Instagram carousel                                         |
| Instagram  | Short caption, strong opening, line breaks, selective hashtags  | 4:5; 1080×1350; JPEG         | The editor can prepare 1–4 ordered images; the publisher supports one image or a carousel of up to 10 JPEG images and a caption up to 2,200 characters |
| Yandex Zen | Article title, explanatory context, headings                    | 16:9; 1600×900; JPEG/PNG     | Article illustrations; no carousel limit is claimed                                                                                                    |
| Site blog  | Useful, fact-based full article with a clear title and headings | 16:9; 1600×900; JPEG/PNG     | One optional cover image; otherwise the site uses its default blog cover                                                                               |

All image ratios/dimensions above are test-workflow editorial recommendations and target output, not universal technical upload limits, except for the platform API limits specifically called out. Square and portrait outputs are tied to the same square master; the landscape edit uses that master as its reference. Keep headlines within the square's safe area so they survive portrait extension and remain available as a reference for the horizontal adaptation. These profiles do not guarantee text-length compliance with every client or API field.

Primary references used when writing the profile:

- Telegram Bot API: <https://core.telegram.org/bots/api>
- MAX attachments: <https://dev.max.ru/docs-api/use-cases/sending-messages/media>
- MAX image limits: <https://dev.max.ru/docs-api/use-cases/sending-messages/attachment-types>
- Meta's Instagram API workspace: <https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api?entity=request-23987686-db99ce99-bf76-475c-8b76-718576c11cae>
- VKCOM API object schema: <https://github.com/VKCOM/vk-api-schema/blob/master/wall/objects.json>

Channel guidance should be verified against platform documentation again before enabling publishing. Keep unverified Dzen/VK pixel sizes as editorial recommendations, not claims about platform constraints.

## Delivery and channel connection status

The content plan accepts VK, Telegram, MAX, Instagram, Yandex Zen, and the site blog as preparation formats. `content-plan-publishing.service.ts` schedules and dispatches `vk`, `max`, `telegram`, `instagram`, and `blog`; unsupported channels are rejected by `verifyTarget` before queueing. The review dialog leaves the schedule action unavailable until a supported channel is configured.

- **VK:** the status endpoint reports configuration when the VK client and community ID are present. Before scheduling, the backend checks the target and publishing rights. The connected community token is used for wall publication and bot messages; `VK_PHOTO_UPLOAD_ACCESS_TOKEN`, when supplied, is used only for the wall-photo upload and save methods. The current VK API schema lists `photos.getWallUploadServer` and `photos.saveWallPhoto` as user-token methods. In a live check the configured community token had `wall`, `photos`, `manage`, and `messages`, but `photos.getWallUploadServer` returned error 27. Image-bearing VK posts now also probe the wall-photo upload address before scheduling and are not queued if VK rejects it or the check fails. Text-only VK posts do not need this photo check. At dispatch, any photo-upload failure stops the post instead of intentionally dropping the image; old production versions may still have the former text-only fallback until updated. Getting an upload address is only a preflight, not proof that saving, attaching and displaying the photo works. The separate token flow has automated mocked tests but still requires a live end-to-end test with suitable access and an explicitly authorized post. `photos.getMessagesUploadServer` accepts the community token, but it is for message photos and is not verified as a reliable source of wall attachments. A successful `wall.post` response alone does not prove that readers can see all attachments.
- **MAX:** the status endpoint separately reports whether the bot is configured and whether a target chat ID exists. Before scheduling, the backend checks that the target is an active broadcast destination (a channel or group chat, not a private dialog) and that the bot is an administrator or has `write`/`admin` permission. A missing `status` field is treated as active; an explicit non-active status is rejected. Permission failures, inactive targets, and unreachable API responses are converted to actionable 409/502 messages and sanitized diagnostics instead of a generic 500. MAX API host `platform-api2.max.ru` uses a certificate chain from the Russian Trusted Root CA, which is not in Node's default trust store. The backend must run with `NODE_EXTRA_CA_CERTS=/app/certificates/russian-trusted-root-ca.pem`; the repository ships `certificates/russian-trusted-root-ca.pem`, the development script sets it, and the production Dockerfile declares it. Removing it breaks both content publishing and MAX bot replies with `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`. MAX Bot API has no method that lists the chats a bot belongs to (`/chats` without an ID answers `404 chat.not.found`), so a chat ID is learned only from updates: the `bot_added` webhook update stores `{chatId, title}` under the `max.publishChannel` app setting, and `GET /api/max/readiness` exposes it as `discoveredPublishChatId`/`discoveredPublishChatTitle`. Publishing tries `MAX_PUBLISH_CHAT_ID` first and falls back to the discovered channel when the configured ID answers `404`; a stale configured ID therefore does not block a channel that the bot reported itself in. Re-adding the bot to the channel is the supported way to (re)discover the identifier.
- **Site blog:** always reports configured. The production scheduler upserts the approved post into `siteContent` under section `blog` with published status. This is a site-content write, not an external social API call.
- **Telegram:** the bot token is server-only in `TELEGRAM_BOT_TOKEN`; `TELEGRAM_PUBLISH_CHAT_ID` selects a numeric chat ID or public `@username`. When the runtime outbound proxy is configured, the backend sends Telegram Bot API requests through it (including multipart media, preserving the generated boundary); it does not fall back to a second transport after an ambiguous request. Before scheduling and again before dispatch, the backend checks that the target is a channel/group and that the bot is present with posting permission (channel bots must be administrators with `can_post_messages`). Text posts use `sendMessage`; posts with images use `sendPhoto` or `sendMediaGroup` (up to 10 images). The bot must be added to the target; a configured token alone is not proof of permission. Telegram does not provide an idempotency key for these send operations, so uncertain/partial results are marked unknown and are not automatically retried.
- **Instagram:** the content-plan tab has an authenticated connection card backed by `GET /api/instagram-publishing/status` and `POST /api/instagram-publishing/connect/start`; the public callback is `/api/instagram-publishing/callback`. OAuth uses Facebook Login, a one-time stored state, and the configured target username to locate the connected professional Instagram profile on an eligible Facebook Page. Required backend variables are `META_INSTAGRAM_APP_ID`, `META_INSTAGRAM_APP_SECRET`, `META_INSTAGRAM_TARGET_USERNAME`, `META_INSTAGRAM_REDIRECT_URI`, and `INSTAGRAM_TOKEN_ENCRYPTION_KEY`; development derives its callback from the backend preview host. Set `META_INSTAGRAM_TARGET_PAGE_ID` to the exact Facebook Page ID shown in Meta Business Suite when known. The connection first checks that Page directly using the signed-in user's token and falls back to the paginated `/me/accounts` list. It verifies the linked Instagram ID and username before saving an AES-256-GCM-encrypted Page token. The Facebook OAuth request includes the five content permissions displayed in this Meta app's setup, including `business_management`; do not substitute the separate Instagram Login app credentials or its `instagram_business_*` scopes. Missing permissions, missing Page visibility, missing Instagram visibility, missing Page token, and a mismatched username produce separate safe callback results and redacted server diagnostics; neither OAuth codes nor access tokens are logged. A Meta UI checkbox is not proof that the same asset is visible through the Graph API, and a 2xx OAuth callback is not proof that the Instagram connection was stored.
  Publishing is implemented in `instagram-publishing.service.ts` through the Meta Graph API (`v26.0`) and the Amazi outbound proxy. Scheduling verifies the stored token with a lightweight `/id` read, and rejects a missing connection, expired token, or missing `instagram_content_publish` permission before queueing. Dispatch uses an existing JPEG media URL when available; other formats are converted to JPEG with `@napi-rs/canvas`, uploaded as a temporary managed-storage object, and removed after the attempt. A single image creates one `/media` container; 2–10 images create child containers with `is_carousel_item` and a `CAROUSEL` container. The publisher polls `status_code` until `FINISHED`, calls `/media_publish`, reads `permalink`, and only then marks the post published. Uploaded JPEG objects are temporary and never reused as the post's media-library item. The scheduler validates a non-empty caption of at most 2,200 characters and requires at least one image. `publishingEnabled` is true only when the OAuth configuration is complete and a non-expired connection is stored; that flag describes the connection, while a real published post is the only proof that delivery works. Public image links are built as `${origin}/api/media/managed/<base64url objectId>`. `PUBLIC_MEDIA_BASE_URL` falls back to `VITE_API_PRODUCTION_URL`, which usually ends with `/api`; that trailing `/api` is stripped before the path is appended, otherwise Meta receives `/api/api/media/...`, the download fails, and the Graph API answers `400` with provider code `9004` "Only photo or video can be accepted as media type".
- **Yandex Zen:** its editorial profile and drafts are available. This account's Dzen channel was confirmed by the owner as linked to the Telegram channel through `@zen_sync_bot` in automatic mode. Scheduling a Zen card therefore converts its queue destination to the configured Telegram channel; the synchronizer is expected to mirror the Telegram message to Dzen. This is not direct Dzen API publishing, and the post also appears in Telegram. Telegram text limit (4,096 characters) applies. Do not separately schedule the same content for Telegram and Zen, or it may be duplicated.

Only a post explicitly approved and separately scheduled is sent. Preview may create a scheduled row, but preview and production share the same managed database; the production-only scheduler consumes due rows. A preview schedule is therefore a real live publication, not a sandbox test. Do not start a second preview scheduler. Keep the confirmation warning visible, and never use ordinary test content in this shared queue without the owner's explicit authorization. During direct Telegram verification, convert upstream/network errors to a safe 502 response so the UI does not present an opaque generic 500; no queue row is created on verification failure.
